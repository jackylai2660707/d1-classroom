# 橋接首次連線準備

2026-10-31：現場只讀調研後，現有機身配置尚不能直接使用預設橋接。此紀錄說明本機修正與分階段準備，不代表真機驗收；機身部署狀態、地址及結果另存忽略的 field-results/。

## 本機原始碼修正

- 隨包 SDK 的標頭與 Python 二進位模組使用 `checkConnect()`；橋接及假 SDK 改用同名介面。原廠部分文字文件寫成 `checkConnection()`，不能只按文件名稱實作。
- 安裝時除匯入 SDK，還檢查 HighLevel 所需方法存在；這一步不建立 HighLevel 實例、不呼叫 initRobot。
- 新增 `sudo bash install.sh --no-start`：檢查前置條件後安裝檔案，但不執行 daemon-reload、enable、restart，不檢查連線、不初始化 SDK。既有橋接若運行或啟用，拒絕此模式，以免覆寫使用中的程式。
- `--no-start` 仍會匯入原廠原生模組，不能將它當作完全被動的只讀檢查。執行它會寫入 /opt/d1-classroom 與 systemd unit。
- systemd 249 在 list-unit-files 未找到服務時會以空輸出回傳 1；只安裝檢查接受這個特定情況，其他查詢失敗仍拒絕繼續。
- 未帶 `--no-start` 的原有命令仍會啟動服務。v2.0.0 Release 和 ZIP 不含本次修正，不能拿舊包當成已修正版；未重建或覆寫正式成品。

## 首次讓現有 UI 控制機器狗的順序

1. 先修正並通過本機核心測試。UI 沿用學生工坊，不新增連線模式。
2. 依該機型／韌體核對原廠允許的機載 SDK 部署方式與算力。原廠 2026-08-04 指南 §5.6 有機載 SDK 範例，但 §6.20 不建議機身部署控制邏輯；不能把範例視為常駐橋接已獲確認。
3. 核對 SDK 回傳地址與運動控制服務的實際綁定地址。目前不能只把 bridge 的 sdk-address 改成 auto 就當作配置完成。不自動修改原廠 sdk_config.yaml、start_motion_control.sh、robot-launch.service，不為測試重啟原廠服務。
4. 確認後才準備修正版暫存初始化包並檢查內容；先以 --no-start 分階段部署。該命令只做準備，不能證明 SDK 連通或動作正確。
5. 現場先確認硬體停止方式、狗的姿態、電量和空場地，再單獨進行首次 SDK 啟動；未確認前不設開機自啟。SDK 可能優先於手柄，不把手柄當作已驗證的緊急停止替代品。
6. 從目前原始碼啟動學生工坊，先在練習模式核對單一 `dog.stand()`；首次實機只測站立，目視確認結果後另一次執行 `dog.lie()`。不先跑整課範例或自動連續動作。

實機地址、MAC、現場輸出及後續結果保存在忽略的 field-results/，不加入交付。軟體測試通過不代表物理停止或實機授課驗收。

## 2026-10-31 後續單機通訊驗證

經使用者授權，在備份、暫時自動還原保護及機身趴穩的條件下，對一台現場機身試設原廠 SDK 回傳及綁定地址為 127.0.0.1，只以原廠管理器單獨重啟運控。SDK 連線與電量讀取、Windows HTTP 狀態與 MAC 廣播掃描均通過；橋接僅手動啟動，未設自啟。詳細改動、觀察與還原方式保存在 field-results/2026-10-31-loopback-connection.md。

這是該台該韌體的通訊證據，尚未測實際換網、開機、物理動作／停止、相機或多狗負載。未將這些原廠設定修改加入通用 install.sh；其他韌體不能自動套用。首次部署仍應按前面的分階段核對流程，不能直接使用舊 Release 初始化包。
