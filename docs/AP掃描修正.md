# AP 掃描修正（2026-10-31）

原橋接只允許 robot.json 的 interface 所在 IPv4 網段發送探索查詢。現場機身使用 wlan0 連路由器、ap0 提供 AP；切 AP 後，PC 即使取得 AP 的 DHCP 地址，也可能因來源網段不同而被橋接忽略。這是程式過濾問題，不能據此宣稱原廠 AP 有封鎖廣播。

## 修正內容

- 每個探索封包到達時，讀取設定的 Wi-Fi 網卡與 ap0 的當前網段。
- 僅納入可辨識為 Wi-Fi、有 IFF_UP 旗標、可讀取 IPv4／遮罩的網卡；無地址、停用、消失或無效／全域網段皆忽略。
- 不寫死 192.168.234.1 或任何 DHCP 地址，不自動開 AP、不新增 Windows 連線模式，也不允許任意 Ethernet／VPN 網段。
- 回覆仍使用原設定網卡的完整 MAC 作穩定身分，不改成 ap0 MAC。回覆封包交由 Linux 對 PC 所在直連網段的路由選擇出口與來源地址。
- SDK 位址、單一控制權、心跳與動作限制均不變。此台機身既有 SDK 回環配置獨立於 Wi-Fi 地址。

## 驗證

新增 6 項假網卡測試：兩網段可探索、只有 AP 有 IPv4、AP 停用／缺失、DHCP 網段改變、Ethernet／VPN 與無效網段排除，以及兩網段保持同 MAC 且探索不取得控制權、不發動作。

根目錄核心測試通過：JavaScript 7；Python 37 中 36 通過、1 項 Windows 不適用跳過；Release 不可變測試 2 通過。沒有修改 renderer 或課程資料，無須重新 bundle。

現場更新、備份與當前路由器模式的回歸檢查見忽略的 field-results/。尚未實際切到 AP 進行廣播／相機／動作驗收，不能把假網卡測試當成 AP 實機通過。

## 離線驗證 AP

先停止程式、確認狗靜止再切 AP。PC 連狗的 Wi-Fi 後確認有正確 DHCP 地址，先檢查橋接狀態，再掃描並核對同一 MAC。AP 沒有網際網路不影響本機學生工坊及已下載模型；Codex 對話仍需網際網路。

橋接目前未設開機自啟：若切 AP 包含重開機，需先 SSH 檢查服務是否 active，不能把服務未啟動誤判為掃描被擋。固定 v2.0.0 Release 尚不包含本修正，未覆寫既有 Release、ZIP 或 manifest。
