# 心跳連線修正（2026-10-31）

現場回報「控制權無效或已過期」。這表示橋接端控制權已失效，不等於已確認 Wi-Fi 斷線。查到並以假 SDK 重現一個可造成相同類型失效的問題：控制指令和心跳共用 Controller.lock，原生 SDK 呼叫延遲時，心跳也會排隊，可能超過 1.2 秒期限。

## 修正

- 心跳改用獨立的控制權鎖，只驗證控制權、接收時間並回覆快取的電量與狀態，不呼叫 SDK。
- SDK 連線與電量查詢仍由原有監看循環每約 0.5 秒更新；SDK 錯誤或低電量時仍取消運行中的程序並嘗試停止。
- 控制權有效期仍為 1.2 秒，未延長。錯誤、過期及舊控制憑證不能恢復控制權；斷線後仍須重新連接，不續跑舊程式。
- UI 將「網路中斷」改為「連線中斷」，保留原始原因，避免把控制權錯誤一律當成 Wi-Fi 問題。
- 原先 HTTP/1.0 會關閉每次回覆的連線；改用有 Content-Length 的 HTTP/1.1，讓心跳可重用 TCP 連線，避免每次重新握手。請求格式或長度錯誤時明確關閉連線，防止未讀完的內容影響後續請求。這不能消除所有網路丟包。

## 驗證及範圍

- 修正前，將假 SDK 站立呼叫阻塞，心跳請求亦無法及時回覆；修正後，模擬動作累計時間超過控制權期限，期間正常送心跳仍保持控制權。
- 新增 6 項測試：慢動作不阻塞心跳、心跳不呼叫 SDK、逾時或錯誤心跳不能恢復控制權、低電量停止、SDK 中斷停止、實際 HTTP 連線重用與錯誤內容關閉連線。
- 核心測試：JavaScript 7 項通過；Python 31 項中 30 項通過、1 項 Windows 不適用跳過；Release 不可變測試 2 項通過。
- 以固定 x64 Node 執行 bundle。開發版假 SDK UI smoke 初次連線等待逾時，加入失敗時 UI 記錄輸出後重跑通過；未將第一次失敗當作已定位的根因。
- 僅分離鎖後的實機無動作測試仍重現過期；進一步量得一次心跳請求耗時約 1.23 秒，而一般成功請求為數十毫秒。之後加入 HTTP 連線重用，再以新版重跑假 SDK UI smoke 通過。不能只因某一輪短測成功就宣稱斷線完全消除。
- 原廠原生函式若佔住 Python GIL、網路丟包或程序被系統暫停，仍可能阻塞整個服務。本修正針對已重現的鎖競爭，不代表所有連線中斷均已消除。
- 本輪未重建正式 Release、ZIP 或 EXE；機身更新、備份與實測數據另存忽略的 field-results/。

後續須在現場依序驗證空閒連線、開相機辨識、單次動作與停止。不要用大量站立／趴下循環作為穩定性測試，也不要為避免過期而關閉斷線停止保護。
